# Modern workflow pages: backend contract

The React shell exposes `/onboarding`, `/home`, `/contacts`, `/research`, `/companies`, `/outreach`, `/replies`, `/meetings`, `/campaigns`, `/content`, `/integrations`, and `/settings`. These pages read typed persisted projections from `app/workflow_views_api.py`, `app/onboarding_api.py`, and the existing domain routers. Writes remain in setup, sales, and marketing action routes. Former `/operations` and `/legacy/operations/*` operator URLs redirect to the corresponding React pages. `/` and the retired `/operations/history` redirect to `/home`; the old operator templates and command form are removed. `/meet` and `/calendar` remain public booking utilities. React is the authoritative operator UI.

| Page | Read projection and existing store | Supported display | Real action |
| --- | --- | --- | --- |
| Home | `GET /company/ui/home`; `sales_leads`, `sales_drafts`, `marketing_campaigns`, `marketing_manual_posts`, active org | Counts and recent persisted contacts/campaigns | Navigation to the corresponding workspaces |
| Outreach | `GET /company/ui/outreach`, `GET /company/ui/outreach/{id}`; joined `sales_drafts` and `sales_leads` | Company, contact, channel, subject/body, exact draft status, timestamps | `POST /company/sales/drafts/{id}/update`, `/approve`, `/send`; founder action token and backend state guards apply |
| Replies | `GET /company/ui/replies`, `GET /company/ui/replies/{id}`; original inbound `sales_interactions` joined to leads | Original subject/body, sender, received time, whether this is the lead's latest interaction, exact thread ID | `POST /company/sales/leads/{id}/draft` only for the latest eligible inbound reply; founder token required; draft is reviewed separately in Outreach |
| Meetings | `GET /company/ui/meetings`, `GET /company/ui/meetings/{lead_id}`; `sales_leads.metadata.meeting` | Manual scheduled marker, optional recorded date/note/source, related contact and company | `POST /company/sales/leads/{id}/schedule-meeting` with founder token records a marker; `/calendar` opens the existing booking page, but does not confirm a booking |
| Campaigns | `GET /company/ui/campaigns`, `GET /company/ui/campaigns/{id}`; `marketing_campaigns`, saved script artifact, video variants | Organization, topic, objective, buyer, platforms, exact stage/status, saved script and errors | `POST /company/marketing/campaigns`, `/campaigns/{id}/approve-script`, `/retry`; approval/retry use founder token |
| Content | `GET /company/ui/content`; latest 200 persisted manual posts and latest 100 active-organization file-backed asset packs | Type, format, workflow stage, Buffer status, caption/source excerpt, saved assets; optional provider state and experimental metrics via `GET /company/marketing/manual-posts/{id}/buffer-insights` for a saved Buffer ID | `POST /company/marketing/asset-packs`; `POST /company/marketing/manual-posts/{id}/buffer-schedule` with founder token and selected configured account |

The projections return backend field names as-is. There is no implicit camelCase conversion. Draft status, campaign status, content stage, and Buffer status are displayed separately. Unknown values render explicitly as unknown. A draft is never labelled sent without the sales send response and refreshed record; a Buffer draft or scheduled post is never labelled published.

The screenshot fields **unsupported by current backend** are outreach owner, due date, follow-up queue, personalization reason, and program; reply intent, confidence, positive/objection classification, extracted signals, and suggested response; meeting booking confirmation, attendees, duration, call link, agenda, outcome, no-show rate, and opportunity value; campaign launch date, attributed leads, impressions/clicks/conversion, and confirmed publication; content owner, review assignee, and approved lifecycle. Content performance is available only when Buffer returns metrics for a saved post ID using a personal API key. The UI omits unsupported fields. Content search and pagination operate on the explicitly bounded loaded set, and the page warns when either source was truncated.

The API client sends Basic auth to read and write routes and `X-Founder-Action-Token` only for the guarded mutations. A 401 ends the frontend session, a 403 leaves it intact, validation and state conflicts display backend errors, and failed refreshes retain prior query data. Relevant React Query keys include URL filters, sort, page, and selection inputs; mutations invalidate only affected workflow queries.
